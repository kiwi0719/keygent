# Weaver 上下文压缩设计

草案 v1 · 2026-10-01

## 一、为什么要压缩

每轮请求都把整段对话重发一遍。对话越长：

1. **越贵**：就算命中缓存按一折算，几十万 token 的上下文每轮也要付几万 token 的钱。
2. **越容易“看漏”**：上下文太长时，中间的细节容易被模型忽略。
3. **可能放不下**：前沿模型窗口约 1M，但 GLM-5 只有 204k，本地模型常见 32k。

压缩就是在快满的时候，把旧内容缩小，让对话能继续。

## 二、核心思路：只移走，不删除

我们有账本。压缩**不改历史**，只是往账本里追加一笔：“从某个位置往前，给模型看的是缩小后的版本”。原文永远留在账本里，以后能找回来（main.md 第 7 课说的新趋势，OpenHands 也是这么做的）。

压缩复用已有的“动作”机制，`kind=compact`，不新增事件类型：

```
ActionStarted(kind=compact, input={reason: threshold | overflow | manual})
ActionCompleted(kind=compact, output={
    mode: "trim" | "summary" | "none",
    upto_seq: 120,          # 这个位置及之前的内容受影响
    summary: "…",           # 只有 summary 才有
    tokens_before, tokens_after,   # 估算值
    usage,                  # 写摘要的模型用量（计入预算）
})
```

好处：崩溃恢复现成（压缩和调模型一样，可以重做）；什么时候压的、压掉了什么、摘要写了什么，账本里都查得到。

## 三、两层：先裁剪，不够再写摘要

**第一层：裁剪（trim）**，不调模型，便宜。
把 `upto_seq` 之前的**工具结果**换成占位符“[旧工具结果已清理，需要时请重新读取]”，旧图片同理。工具调用本身保留，模型知道自己做过什么。

**第二层：摘要（summary）**，调模型，贵、会丢细节。
把 `upto_seq` 之前的对话整体换成一条摘要，后面的原样保留。

**怎么选**：

```
目标 = 阈值 × 60%                          # 压完后留出余量，免得每轮都压
需要腾出 = 当前估算 − 目标
裁剪能腾出 = “最近 20k token 之前”的工具结果总量
裁剪能腾出 ≥ 需要腾出，且 ≥ 20k            → 只裁剪
否则                                        → 写摘要
摘要失败                                    → 退回机械方案：不调模型，只保留用户原话
```

“至少腾出 20k 才裁剪”是为了缓存：每次压缩都会让缓存失效一次，腾得太少不划算。

小窗口时两个固定值按阈值缩小：“原样保留”取 min(20k, 阈值 ÷ 4)，“至少腾出”取 min(20k, 阈值 ÷ 10)。否则 32k 的窗口（阈值 16k）光“原样保留 20k”就超了，永远压不下去。

## 四、什么时候压（阈值）

两种算法取较小的，先到哪个按哪个：

```
预留 = 模型输出上限 max_tokens + 单轮工具结果上限（默认 30k）
阈值 = max(min(窗口 × 85%, 窗口 − 预留), 窗口 × 50%)    # 不低于一半：防止小窗口时预留减过头
阈值 = min(阈值, 软上限)                                # 设了软上限才有这一步
```

- 小窗口靠“预留”保证不撑爆；大窗口靠“百分比”保证不压得太满。
- 软上限 `WEAVER_COMPACT_AT` 默认关，想省钱时开。
- 窗口大小：`WEAVER_CONTEXT_WINDOW` > OpenRouter 模型列表自动读取（缓存一天）> 默认 128k。

**当前上下文有多大**：用上一次模型回复里的真实 `input_tokens + output_tokens`，加上之后新增内容的估算（字节数 ÷ 3）。压缩后到下一次模型回复前，用压缩时的估算值。

**三种触发**：

| 触发 | 条件 | 做法 |
|---|---|---|
| 阈值 | 调模型前，估算 ≥ 阈值 | 压缩一次，然后调模型（刚压过就不再压，防止死循环） |
| 超长 | 模型报“上下文超长”（HTTP 错误或 Anthropic 的 `model_context_window_exceeded`） | 强制压缩后重试一次；还放不下就结束，状态 `error` |
| 手动 | `python3 -m weaver -s <id> --compact` | 立刻压缩一次 |

## 五、摘要怎么写

**切点**：保留最近约 20k token 原样。切点只能落在“一条模型回复之前”或“一条输入之前”，**永远不把工具调用和它的结果拆开**。

**摘要请求用原文**：切点之前如果有被裁剪过的工具结果，写摘要时从账本取原文，不给模型看占位符。实测中模型对着占位符会编造内容（把 main.md 编成了“Cozo 数据库教程”）。原文加起来超过阈值才退回裁剪后的版本，并在要求里写明“看不到的内容不要猜”。代价：前面有裁剪时，摘要请求只有裁剪点之前的部分能命中缓存。

**摘要请求**：发“切点之前的对话 + 一条写摘要的要求”，工具定义照带、但禁止调用工具。这样请求的开头和主对话一样，能命中缓存，很便宜（DeepSeek Harness 的做法）。如果之前压缩过，切点之前的对话本身就以上一次的摘要开头，要求模型**合并**而不是重写。

**摘要模板**（各家已收敛的版本）：目标、约束和偏好、已完成、关键文件和代码位置、错误和修复、当前状态、下一步。路径、函数名、报错、ID 原样保留。

**用户原话**：不交给模型，由代码原样附在摘要后面（从新到旧，最多 2 万字）。模型说过的话和工具输出都能丢，用户的原话是需求的唯一来源（Codex 的观点）。

**摘要消息**长这样（作为一条 user 消息，包在 `<system-reminder>` 里）：

```
此前的对话已压缩成下面的摘要。完整记录仍保存在账本里。请直接接着工作。

<摘要>

## 用户原话（原样，从新到旧）
- …
```

## 六、和缓存的关系

- 压缩决定记进账本，投影时照着执行。所以前缀**只在压缩那一刻变一次**，之后又稳定。不能在投影时动态算“最近 N 条”，那样前缀每轮都变。
- 测试：两次压缩之间，前缀不变。

## 七、放在哪一层

| 部分 | 位置 |
|---|---|
| 什么时候压（估算、阈值、防死循环、超长重试） | 内核 `decide` + Policy |
| 怎么压（裁剪还是摘要、切点、写摘要） | Runtime：`weaver/compaction.py` |
| 压完给模型看什么 | 投影 `project` |
| 识别“上下文超长”错误 | 模型适配器 |
| 窗口大小 | 配置 / OpenRouter 模型列表 |

## 八、测试

1. 投影：裁剪、摘要、多次叠加的效果正确。
2. 切点不拆开工具调用和结果；用户原话一条不丢。
3. 两次压缩之间前缀不变。
4. 摘要请求：开头和主对话一致、禁止调用工具。
5. 阈值计算：小窗口、中窗口、1M 窗口、软上限。
6. 阈值触发 → 压缩 → 调模型；刚压过不再压。
7. 超长报错 → 压缩 → 重试；再超长 → error。
8. 压缩中途崩溃 → 重做。
9. 摘要失败 → 退回机械方案。
10. 真实验证：把窗口设小，连续读文件，看到先裁剪、再摘要，之后缓存恢复命中。

## 九、暂不做

压缩前先写长期记忆、让模型自己决定压缩、分段写摘要、压缩后重读最近的文件、查找被压掉的原文的工具。
