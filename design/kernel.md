# Weaver 内核设计

v6 · 2026-10-01（和代码同步：压缩、背景输入、权限拒绝、预算折算、并行写回、子 Agent）

这份文档讲 Weaver 的“内核”怎么设计：它是什么、为什么这么做、具体怎么运转。

---

## 一、我们要解决什么问题

一个最简单的 Agent 就是一个循环：问模型 → 模型说要用工具 → 执行工具 → 把结果告诉模型 → 再问模型……直到模型说“做完了”。

这个循环写成一个 `while` 就能跑，但它有几个硬伤：

1. **进程一挂，全丢**。跑到一半断电了，不知道做到哪一步，也没法接着做。
2. **不能停下来等人**。遇到“删文件前要你点头”，只能卡在 `input()` 上。如果人三个小时后才回复，进程就得干等三个小时。
3. **只能在本地跑**。想把它搬到服务器上、让手机或 Slack 来操作它，得重写。
4. **不好测试**。逻辑和“调模型、读文件”搅在一起，测一个分支就得真的调一次模型。

我们想要的是：**同一个内核，本地能跑，服务器也能跑；随时能停，随时能接着跑；每一步的逻辑都能单独测。**

## 二、核心思路：记账本

把 Agent 想象成一个**只会记账、从不涂改的会计**。

- 发生的每一件事都记一笔：“用户说了 X”“开始调模型”“模型回复了 Y”“开始执行工具”“工具返回了 Z”……
- 账本**只能往后写，不能改、不能删**。
- 任何时候想知道“现在是什么情况”，就从头翻一遍账本算出来。
- 想知道“下一步做什么”，就看当前情况，按一张固定的规则表决定。

这样做的好处，正好对应上面四个硬伤：

| 硬伤 | 记账本怎么解决 |
|---|---|
| 进程挂了全丢 | 账本在磁盘上。重启后翻一遍，就知道做到哪了，接着做。 |
| 不能等人 | 在账本上记一笔“正在等你审批”，进程可以直接退出。等人回复了，记一笔“批准了”，再把进程叫起来，翻账本接着做。 |
| 只能在本地 | 账本存在哪、谁来执行动作，都是可替换的零件。本地用文件，服务器用数据库，内核不变。 |
| 不好测 | “看账本决定下一步”是一个纯计算，不碰网络和文件。给它一本假账本，看它的决定对不对就行。 |

整个内核只有三个动作：

```
翻账本，算出现状          fold(账本)            → 现状
看现状，决定下一步        decide(现状, 规则)     → 要做的事
把账本翻译成模型看的对话  project(账本)          → 发给模型的消息
```

真正去调模型、执行工具的，是内核外面的**执行者（runner）**。它拿到“要做的事”，去做，然后把结果记到账本上。然后循环：再翻账本，再决定，再做。

```
 账本 ──► 翻一遍 ──► 现状 ──► 决定 ──► 要做的事 ──► 执行者去做
  ▲                                                  │
  └──────────────── 把结果记进账本 ◄──────────────────┘
```

## 三、走一遍例子

你说：“帮我看看 main.md 第一行写了什么。”

账本上会依次出现：

```
#1  开始一次任务
#2  收到输入：用户说“帮我看看 main.md 第一行写了什么”
#3  输入审核：接受
#4  开始调模型
#5  模型回复完成：我要调用 read_file(main.md, limit=1)
#6  开始执行工具 read_file
#7  工具完成：“# 开源 AI Agent 架构教程……”
#8  开始调模型
#9  模型回复完成：“第一行是标题：开源 AI Agent 架构教程……”（没有再调工具）
#10 任务结束：完成
```

每一步之后，内核都会翻一遍账本，决定下一步：

- 看到 #3（有了一条已接受的输入）→ 该问模型了。
- 看到 #5（模型要调工具，但还没结果）→ 去执行工具。
- 看到 #7（工具结果都齐了）→ 再问模型。
- 看到 #9（模型没有再要工具）→ 结束。

**如果在 #6 之后进程崩了呢？** 重启翻账本，发现“开始执行工具”记了，“工具完成”没记。内核不知道工具到底执行没执行（如果是删文件，可能已经删了一半），所以它**不会自作主张重做**，而是补记一笔：“工具执行中断，结果未知”，交给模型自己判断怎么办。

**如果在 #4 之后崩了呢？** 调模型没有副作用，重发一次就行。

## 四、几个关键概念

### 1. 会话和任务

- **会话（Session）**：一整段长期的对话，对应一本账本。
- **任务（Run）**：会话里的一次“你交代、它做完”。你说一句话，它干完，就是一个任务；你再说一句，就是下一个任务。

“完成了”“被取消了”“预算用完了”这些状态，属于任务，不属于会话。一个任务结束了，会话还在。

### 2. 账本上记什么（9 种事件）

| 事件 | 大白话 |
|---|---|
| 任务开始 | 一次新任务开始了 |
| 收到输入 | 有人或有东西说了话 |
| 输入审核结果 | 这句话收不收 |
| 动作开始 | 开始调模型 / 执行工具了 |
| 动作完成 | 模型回复了 / 工具返回了（或出错了） |
| 开始等待 | 停下来等某件事（等你审批、等你回答、等定时器） |
| 等待结束 | 等到了 |
| 取消 | 用户喊停 |
| 任务结束 | 这次任务结束了，附带结束原因 |

有几点设计说明：

**为什么“动作”要分“开始”和“完成”两笔？** 为了崩溃恢复。只记“完成”的话，崩溃后分不清一个工具是“还没开始”（可以放心执行）还是“执行了一半”（结果未知）。

**为什么模型回复和工具结果都叫“动作完成”？** 它们本质一样：都是内核让执行者去做一件事，做完了拿回结果。统一成一种事件，崩溃恢复只要一套逻辑。用一个 `kind` 字段区分：调模型（`model`）、执行工具（`tool`）、压缩上下文（`compact`，见 compaction.md）。子 Agent 不是单独的 kind：它就是一个叫 `task` 的工具，内部递归跑同一个内核（见 parallel-subagent.md）。

**为什么“等待”是通用的，而不是专门的“等审批”？** 以后要等的东西会越来越多：等审批、等你回答问题、等定时器、等外部回调。内核只需要知道“有件事还没等到，先停下”，不需要知道具体在等什么。

**有些“动作完成”没有对应的“动作开始”**：比如工具被取消了、被你拒绝了、参数被截断了、崩溃后结果未知。这些情况工具根本没真的执行，内核直接补记一条“出错了”的结果，标记为 `synthetic`（合成的）。为什么一定要补？因为模型那边的规矩是：**每个工具调用都必须有一个结果**，缺一个，下次请求就会报错。

### 3. 输入不只是文字

“收到输入”的内容是一组片段，可以混着文字、图片、文件、音频：

```
[文字: "看看这张报错截图"] [图片: blob://sha256-ab12…]
```

**图片、文件不直接放进账本**，只放一个引用（按内容算出的哈希值），实际文件存在一个单独的仓库（`BlobStore`）里。因为账本要经常从头翻，塞进大文件会越来越慢；同一张图被引用多次，也只存一份。

每条输入还标明**是谁说的**：

- `source`（来源）：`user` 是人说的；`policy` 是内核的规则说的（比如“测试没过，继续改”）；`system` 是环境变化（比如“文件被外部修改了”）；`trigger` 是定时器或外部事件唤醒；`context` 是背景信息（环境信息、记忆快照，见 environment.md、memory.md）。不是人说的话，发给模型时会包在 `<system-reminder>` 里，免得模型把系统提示当成你的要求。
- `context` 来源比较特殊：**只提供背景，不开启任务，也不算“新输入”**；压缩时永远保留（排在摘要前面）。
- `author`（发送者）：以后接 IM、群聊时用。你本人私聊和群里陌生人说的话，权限应该不一样。

模型的回复也同样是一组片段：文字、思考过程、工具调用、生成的图片，按模型输出的原始顺序保存。

### 4. 规则（Policy）：内核不自己拿主意

内核只管按流程走。遇到需要**判断“该不该”**的地方，就去问“规则”。可以把内核想成流水线，规则就是站在几个关卡上的质检员。**换一组质检员，就是不同的产品；流水线不用改。**

| 关卡 | 内核问 | 规则答 | 例子 |
|---|---|---|---|
| `on_input` | 这条输入收不收？ | 收（可附带权限范围）/ 拒绝 / 先等人确认 | 群里陌生人让你删文件 → 拒绝 |
| `wait_for` | 这个工具调用能直接执行吗？ | 直接执行 / 先等 / 直接拒绝（`Deny`） | `npm test` 要你点头；`sudo` 直接拒绝 |
| `on_model_done` | 模型说做完了，真完了吗？ | 完了 / 没完，附上原因 | 跑一遍测试，不过就打回 |
| `should_compact` | 上下文快满了吗，要不要先压缩？ | 要 / 不要 | 超过阈值就压（阈值算法见 compaction.md） |
| `limits` | 最多跑几步、花多少 token？ | 数字 | 20 步、100 万 token（折算后，见下一节） |
| `retry_safe` | 崩溃后这个动作能重做吗？ | 能 / 不能 | 调模型、压缩能，执行命令不能 |

默认规则很宽松：输入都收，工具都直接执行，模型说完就算完，超限后给一次收尾机会，只有调模型和压缩可以重做。CLI 用的是它的子类 `PermissionPolicy`（`weaver/permissions.py`），在 `wait_for` 里加了权限规则（见 write-tools.md）。

**输入审核的结果要记进账本**，而不是每次翻账本时重新审核一遍。因为规则以后可能会改，如果重新审核，昨天收下的话今天可能变成拒绝，历史就对不上了。**凡是会影响后续走向的判断，都作为事实记下来。**

### 5. 预算用完怎么办

不直接掐断。先把手头的工具结果补齐，然后告诉模型“预算用完了，别再调工具，总结一下做了什么、还剩什么”，禁用工具再问一次模型，然后结束。这样你至少能拿到一份交代。

**token 怎么算**（`kernel.billable`）：没命中缓存的输入 + 命中缓存的输入 × 0.1 + 输出。每轮都重发整段上下文，如果命中缓存的部分也按全价累计，几十轮就把预算“花光”了，实际却没花多少钱（子 Agent 实测里踩过）。工具结果带 `usage` 时（比如子 Agent），也按这个算法计入本任务。

## 五、内核怎么决定下一步（规则表）

内核每次翻完账本，就从上往下检查这张表，**第一条符合的就照做**：

| # | 如果…… | 就…… |
|---|---|---|
| 0 | 有还没审核的输入 | 逐条审核，把结果记进账本；需要人确认的，开始等待 |
| 1 | 任务已经结束 | 如果又有新的已接受输入，开始一个新任务；否则什么都不做 |
| 2 | 用户喊了取消 | 给所有还没结果的工具调用补一条“已取消”，结束任务 |
| 3 | 有动作“开始了但没完成”（只在崩溃恢复时出现） | 能重做的（调模型、压缩）就重做；不能重做的补一条“执行中断，结果未知” |
| 4 | 有事情还在等 | 停下，等 |
| 4b | 模型报“上下文超长” | 这次任务里还没因此压缩过 → 强制压缩；刚压缩过 → 再问一次模型；压缩过还超长 → 结束（`error`） |
| 5 | 模型回复被截断，而且里面有工具调用 | 参数可能只写了一半，不执行，每个都补一条“参数被截断，请重试” |
| 6 | 模型要调的工具还有没执行的 | 逐个看：规则直接拒绝的，补一条“被权限规则拒绝”；需要等审批的，开始等待；被人拒绝的，补一条“用户拒绝”；其余的，执行 |
| 7 | 已经做过预算收尾 | 结束任务（原因：预算用完） |
| 8 | 模型这次没要工具 | 如果是被拒绝、截断或异常，按原因结束；如果是正常说完了，问规则“真完了吗”：完了就结束，没完就把原因作为一条输入记下，再问模型 |
| 8b | 上下文快满了（`should_compact`），且上次模型回复之后还没压缩过 | 先压缩 |
| 8c | 上次模型回复之后还没有新输入时，问 `policy.guard` | 卡住：停下（`stuck`）或暂停问人；要提醒：插一条提醒（todo、打转、预算）再问模型 |
| 9 | 步数或 token 超了 | 禁用工具，再问模型一次，让它收尾 |
| 10 | 其他情况 | 问模型 |

判断“继续还是停”，看的是**模型这次有没有要调工具**，而不是模型给的停止原因。停止原因只用来区分截断、拒绝这些特殊情况。

## 六、执行者（runner）

执行者就是一个很简单的循环：

```
反复：
    翻账本 → 算出现状 → 内核决定要做什么
    没事可做，或者要等 → 退出
    要做的事：
        调模型 / 执行工具 / 压缩这类“真动手”的 → 先记“开始”，做，再记“完成”
        其余的（审核结果、补错误、开始等待、开始/结束任务）→ 直接记进账本
```

两个补充（见 parallel-subagent.md、environment.md）：

- **并行**：内核一次给出一批工具调用时，执行者把相邻的、能并行的（工具自己声明）凑成一批并发执行；先记下这批的“开始”，谁先完成先记谁。投影时再按调用顺序排，所以账本里的完成顺序不影响发给模型的内容。多线程写账本时加锁，同一会话仍只有一个写者。
- **背景输入**：每条用户输入之前，执行者问一遍背景提供者（环境、记忆），内容变了才在末尾追加一条 `context` 输入。

本地和服务器的执行者只有一个区别：

- **本地**：遇到“等待”，就在终端里直接问你，记下你的回答，然后接着跑。
- **服务器**：遇到“等待”，进程直接退出。等手机或 Slack 上有人回复了，记一笔，再把进程叫起来接着跑。

内核本身完全一样。

## 七、必须永远成立的规则（每条都写成测试）

1. 每个工具调用，最终有且只有一个结果。
2. 发给模型的消息永远合法：模型的工具调用后面紧跟着全部结果；中途插进来的话排在结果后面。
3. 账本在任何位置被截断（模拟崩溃），重新翻一遍都能决定出合法的下一步，最终能走到结束。
4. 同一个现状、同一套规则，内核的决定永远一样。
5. 没被接受的输入，永远不会发给模型，也不会开启任务。
6. 每个任务恰好有一笔“任务开始”，最多一笔“任务结束”；结束后不再有这个任务的记录。

## 八、挂在内核外面的部分

内核之外的部分各有设计文档（总览见 `design/README.md`）：模型接入与流式（providers.md）、缓存（cache.md）、压缩（compaction.md）、记忆（memory.md）、环境信息（environment.md）、读和搜索工具（tools.md）、写工具与权限沙箱（write-tools.md）、并行与子 Agent（parallel-subagent.md）。

这些功能加进来时，内核只动过几处，都是小改动：压缩（`compact` 动作、规则 4b 和 8b）、背景输入（`context` 来源）、权限拒绝（`Deny`）、预算折算（`billable`）、工具用量计入预算。还没做的：MCP、skills、服务器版执行者、定时任务等。

## 附录：规格（写代码时对照）

### A. 事件字段

每个事件都有：`seq`（在会话内递增，排序只看它，不看时间戳）、`id`、`ts`、`session_id`、`run_id`、`parent_id`（子 Agent 用，可空）。

| 事件 | 产生者 | 字段 |
|---|---|---|
| `RunStarted` | runner | — |
| `InputReceived` | 前端 / Policy / 外部 | `content: [Part]`、`source`、`author?`；`context` 来源另有 `context_kind`、`digest` |
| `InputJudged` | runner（调用 Policy） | `input_id`、`verdict`、`reason?`、`scope?` |
| `ActionStarted` | runner | `action_id`、`kind`、`input` |
| `ActionCompleted` | runner | `action_id`、`kind`、`output`、`is_error`、`synthetic?`、`usage?`（工具带出来的模型用量，计入预算） |
| `WaitStarted` | runner | `wait_id`、`kind`、`payload` |
| `WaitResolved` | 前端 / 外部 | `wait_id`、`value` |
| `Cancelled` | 前端 | `reason` |
| `RunFinished` | runner | `status`、`text` |

- `source`：`user` / `policy` / `system` / `trigger` / `context`。`policy`、`system`、`context` 来源的输入由内核或 Runtime 自己产生，直接接受，不经审核；`context` 不开启任务、不算新输入。旧账本里记忆快照用的 `memory_digest` 字段仍被认出来。
- `author`：`{id, channel, trust}`，trust 为 `owner` / `member` / `external`。内核不解读，只交给 Policy。
- `verdict`：`accept` / `reject` / `hold`。`hold` 会同时 `WaitStarted(kind=approval)`，确认后补一条 `InputJudged(accept)`。
- 任务的权限范围 `scope` = 触发它的那条输入的 scope。
- Wait 的 `kind`：`approval` / `user_input` / `timer` / `external`。

### B. 片段（Part）

输入：

```
{type: "text",  text}
{type: "image", ref, mime}
{type: "file",  ref, name, mime}
{type: "audio", ref, mime}
```

模型回复（按原始顺序）：

```
{type: "text",      text}
{type: "reasoning", text?, opaque?}           # opaque：厂商的签名/加密内容，原样回传
{type: "tool_call", id, name, args, raw_args} # args 解析失败时为 null
{type: "image",     ref, mime}
```

- 工具调用列表从 `content` 里的 `tool_call` 片段推导，不单独存。
- 最终回复文字 = 所有 `text` 片段拼起来。
- 流式输出的中间片段不进账本，只推给前端。

### C. 动作的 kind

| kind | input | output | 崩溃后可重做 |
|---|---|---|---|
| `model` | 模型名、tool_choice、wrap_up | `content: [Part]`、`stop`、`usage`；失败时 `error`、`error_kind`（`context` 表示上下文超长） | 是 |
| `tool` | `call_id`、`name`、`args` | 工具输出文字（子 Agent 的 task 工具也是它） | 否（由 Policy 声明） |
| `compact` | `reason`（threshold / overflow / manual） | `mode`（trim / summary / none）、`upto_seq`、`summary?`、`tokens_before`、`tokens_after`、`usage?` | 是 |

`stop` 统一为：`end` / `tool_calls` / `truncated` / `refusal` / `context_exceeded` / `other`。

### D. 现状（fold 的结果）

```
run_id, status      running / waiting / done / truncated / refusal / budget / cancelled / error / stuck
in_flight           有“开始”没有“完成”的动作
pending_calls       最近一次模型回复里、还没有结果的工具调用（保持顺序）
unjudged_inputs     还没审核的外部输入
scope               当前任务的权限范围
open_waits          还没等到的等待
last_model_reply    最近一次模型回复
queued_inputs       已接受、但工具结果还没补齐时到达的输入
steps, tokens       本任务的计数（tokens 按 billable 折算，含工具带出来的用量）
wrapped_up          是否已做过收尾调用
overflow_compactions 本任务里因为“上下文超长”压缩过几次
# 会话级（跨任务）：
ctx_base, ctx_growth_bytes   上下文大小估算：上次模型回复的真实用量（或压缩后的估算）+ 之后新增字节 ÷ 3
last_model_seq, last_compact_seq   用来判断“刚压缩过”，防止连续压缩
```

### E. Policy 接口

```python
on_input(input, state)  -> Accept(scope?) | Reject(reason) | Hold(reason)
wait_for(call, state)   -> WaitSpec | Deny(reason) | None
on_model_done(state)    -> Finish | Continue(feedback)
should_compact(state)   -> bool
guard(state)            -> Stop(reason) | Escalate(reason) | Nudge(kind, text) | None
limits                  -> max_steps, token_budget
compact_threshold       -> int
retry_safe(kind)        -> bool
```

### F. 存储

- `EventStore.append(session_id, events, expected_seq)`：seq 对不上就失败，重新翻账本再试。同一会话同一时刻只有一个写者。
- `EventStore.load(session_id)`。
- `BlobStore.put(bytes) -> ref`、`BlobStore.get(ref)`。本地用目录，服务器用对象存储。

### G. 投影（project）

`project(events, blobs) -> messages`：

- 只投影已接受的输入；非 `user` 来源的包进 `<system-reminder>`；片段按具体模型的格式展开。
- `ActionCompleted(model)` → assistant 消息，按片段顺序保留思考过程和工具调用。
- `ActionCompleted(tool)` → 工具结果。
- 同一条模型回复的工具结果**按调用顺序**写回（并行执行时完成顺序是乱的）；结果补齐之前到达的输入，排在这一轮结果之后。
- 失败、被拒、上下文超长的模型回复不进投影。
- 压缩在这一层生效：裁剪把 `upto_seq` 之前的工具结果换成占位符；摘要把 `upto_seq` 之前的内容换成一条摘要，`context` 输入原样保留在摘要前面（见 compaction.md、memory.md）。
- 缓存断点由 `weaver/cache.py` 在投影结果上加标记，各适配器翻译（见 cache.md）。

### H. 实现时补上的细节（v5 → 代码）

代码在 `weaver/kernel.py`，规则表按下面的实际顺序执行，比第五节多了几条：

1. 规则 0～4 同第五节。
2. **模型调用失败**（适配器重试后仍失败），且之后没有新输入 → 结束，状态 `error`。
3. **模型拒绝** → 它回复里的调用都补“模型拒绝”，结束，状态 `refusal`。被拒的回复不进投影。
4. **收尾回复**（规则 7 提前到截断之前）→ 其中的调用都补“预算已用完”，结束。
5. 规则 5、6、8、9、10 同第五节。规则 6 额外处理：参数不是合法 JSON 的调用直接补错误，不执行。
6. 规则 8 只在“最后一次模型回复之后没有新输入”时生效；有新输入（插话、规则反馈）就走到规则 10 再问模型。

其他约定：

- 工具动作的 `action_id` 就是模型给的 `call_id`；重做模型调用时沿用原 `action_id`。
- 输入的 `hold` 等待不阻塞正在进行的任务，只阻塞这条输入本身；规则 4 只看工具调用的等待。
- 状态多了 `error`：模型调用失败，或停止原因无法识别。
