# Weaver 并行执行工具 & 子 Agent 设计

草案 v1 · 2026-10-01

## 一、并行执行工具

### 1. 要解决什么问题

模型一次回复常带好几个调用（实测里一轮发 3 个 grep、2 个 read_file）。现在执行者一个接一个跑，互不相关的查找白白排队。子 Agent 做好之后更明显：派 3 个子 Agent 去查不同的东西，串行要等 3 倍时间。

内核其实已经准备好了：规则 6 一次返回这一批调用的全部 `Execute`。要改的只是执行者“怎么跑这一批”。

### 2. 主流做法（main.md 第 4 课）

- **能不能并行由工具声明，内核只负责分批**：Claude Code、Codex 都是“默认不能，工具自己声明能”。Claude Code 还看输入：同一个 Bash，只读命令可以并发，写命令独占。
- **乱序完成，按序写回**：谁先跑完都行，但写回历史时按模型发出的顺序排，每个调用配上自己的结果。
- **一个失败不连累别人**：各自变成错误结果。（Claude Code 只让 Bash 的失败取消同批其余调用，我们先不做。）

### 3. 我们的做法

**工具声明**：每个工具多一个判断 `concurrency_safe(args)`：

| 工具 | 能并行吗 |
|---|---|
| read_file、grep、find_files | 能 |
| bash | 只读命令能（复用权限模块的 `is_readonly_command`），其余不能 |
| write_file、edit_file、remember、forget | 不能 |
| task（子 Agent） | `explore` 模式（只读子 Agent）能；`general` 模式不能 |

**分批**（Claude Code 的做法）：按模型发出的顺序扫一遍，**相邻的**能并行的调用凑成一批一起跑；遇到不能并行的，等前面跑完，它单独跑。

```
[grep, grep, read_file, edit_file, read_file, bash(npm test)]
 └──── 一批并发 ────┘   └ 独占 ┘  └ 单独 ┘   └── 独占 ──┘
```

**账本**：

- 一批开始时，先把这批的 `ActionStarted` 都记下；每个调用跑完就记它的 `ActionCompleted`（按完成先后）。
- 崩溃恢复不用改：规则 3 本来就会逐个处理“开始了没完成”的动作。
- 多个线程往账本里写，执行者加一把锁（同一会话仍然只有一个写者）。

**按序写回**：投影时，同一条模型回复里的工具结果**按调用顺序**排，不按账本里的完成顺序。账本记录一旦写下就不变，所以投影结果稳定，缓存前缀不受影响。这是内核侧（投影）唯一的改动。

**上限**：同时最多 8 个（`WEAVER_MAX_PARALLEL`）；子 Agent 同时最多 4 个。

**暂不做**：边生成边执行（参数一完整就开跑）、Bash 失败取消同批、同一文件的写入加锁并行（Pi 的做法；我们的写操作一律独占，更简单）。

## 二、子 Agent

### 1. 它的价值是什么

main.md 第 16 课的结论：**子 Agent 的核心价值是隔离上下文（上下文防火墙），其次才是并行。**

主 Agent 要回答“这个项目的错误处理是怎么做的”，自己查可能要 grep 十几次、读二十个文件，这些中间结果全堆进主上下文。交给子 Agent：它在自己的上下文里查完，只交回一段结论。主上下文只多了一条工具结果。

### 2. 主流做法

- **主从派活是共识**：主 Agent 调一个工具（`task` / `Agent` / `spawn_agent`）派活，子 Agent 的最终回复变成这个工具的结果。团队协作（互发消息、任务板）是前沿，复杂一个量级，先不做。
- **默认全新上下文**：子 Agent 只拿到任务描述，看不到主对话。所以**任务描述要写全**。分叉（继承主对话）正在兴起，先不做。
- **普遍保守**：深度 1 层（子 Agent 不能再派子 Agent），并发个位数。
- **做减法**：Hermes 的子 Agent 不加载记忆、不能写记忆；OpenClaw 给子 Agent 用精简版提示词。
- **分工**：派不派、派几个、任务怎么写由模型决定；深度、并发、隔离、权限、结果回传由 Runtime 决定。

### 3. 我们的做法

**工具**：

```
task(description, prompt, mode="explore")
  description  3~5 个字的任务名，显示用
  prompt       完整的任务说明（子 Agent 看不到主对话，要写清楚背景、要查什么、要交回什么）
  mode         explore：只读，用来查资料、读代码、定位问题，可以并行
               general：能改文件、跑命令，用来完成一个独立的子任务，独占执行
```

**子 Agent 就是递归跑同一个内核**：新建一个执行者，用同一个模型、同一套内核规则，只是：

| 方面 | 子 Agent |
|---|---|
| 账本 | 自己的一本，`<父会话>--<子任务 id>`；每个事件带 `parent_id` 指回父会话里那次调用 |
| 上下文 | 全新：环境信息 + 用户原话摘录 + 任务说明；**不加载记忆**（见第 5 节） |
| system prompt | 精简版：“你是子 Agent，完成任务后用一段话汇报结论，写明文件路径、行号和关键发现；不要问用户问题” |
| 工具 | explore：read_file、grep、find_files、只读 bash；general：再加 write_file、edit_file、bash。**都没有 task**（深度 1）、没有 remember / forget |
| 权限和沙箱 | 继承父级：同一个工作目录、同一个沙箱、同一个 `--yes`；要问人时用父级的审批方式（终端里直接问） |
| 限额 | 步数 30；token 预算单独算，用量**计入父任务的预算** |

### 4. explore 和 general 怎么区分

**模型来选，Runtime 来保证。** 和主流一样：派不派、派哪种由模型决定，能做什么由 Runtime 管住。

**模型怎么选**：主 Agent 调 `task` 时自己填 `mode`。判断标准写在工具说明里，只有一个问题——**这个子任务需不需要改动任何东西？** 不需要就 `explore`，需要就 `general`。不填默认 `explore`（更安全，也能并行）。

| 任务 | 模式 |
|---|---|
| 找出所有调用 `getUser` 的地方，判断哪些没做空值检查 | explore |
| 这个项目的错误处理是怎么设计的 | explore |
| 看看测试为什么失败、找出原因（只读代码和日志） | explore |
| 给 `utils.py` 补单元测试并跑通 | general |
| 把 `config.py` 的超时从 30 改成 60，然后跑测试 | general |

**Runtime 怎么保证**：模式决定子 Agent **手里有什么工具**，是硬限制，不是“要求它别改”（第 17 课：约束靠 Runtime，不靠模型自觉）。

| | explore | general |
|---|---|---|
| read_file / grep / find_files | ✓ | ✓ |
| bash | 只读命令（写命令直接拒绝，不问人） | ✓（照常走权限和沙箱） |
| write_file / edit_file | 没有这两个工具 | ✓ |
| 并行 | 能 | 独占 |

**选错了会怎样**：

- 该 general 选了 explore：子 Agent 发现要改文件但没有写工具，会在汇报里写“需要修改 X，但我是只读模式”；主 Agent 自己改，或重新派一个 general。多一个来回，不会出错。
- 该 explore 选了 general：结果照样对，只是不能和别的并行，权限也大了点。工具说明里强调“只是查资料一律用 explore”。

**和主流对照**：OpenCode 的内置子 Agent 就叫 `explore` 和 `general`；Claude Code 有 `Explore`、`general-purpose`、`Plan` 等，也是按工具集区分。它们都支持自定义类型（Claude Code 的 `.claude/agents/*.md`、OpenHands 的 `.agents/agents/*.md`：一个 Markdown 文件定义一种子 Agent 的提示词和工具集）；我们以后可以加 `.weaver/agents/*.md`，第一版只内置这两种。

**撤销**：general 子 Agent 改的文件记在**父会话**的撤销日志里，`python3 -m weaver -s <父会话> --undo` 能一并撤销。

### 5. 子 Agent 的上下文

四种做法的比较（第 16 课）：

| 做法 | 子 Agent 看到什么 | 好处 | 代价 | 代表 |
|---|---|---|---|---|
| 全新上下文 | 只有任务描述 | 小、干净，隔离最彻底 | 背景全靠主 Agent 写，写漏了就跑偏（“任务描述失真”） | 几乎所有项目的默认 |
| 分叉 | 主对话完整历史 + 任务 | 什么都知道，不用重新交代 | 每个子 Agent 都背着整段历史，隔离失效；容易被无关历史带偏 | Claude Code、Codex V2、OpenClaw |
| 快照 / 摘要 | 主对话的只读快照或压缩版 | 折中 | 多一次写摘要的调用，摘要也会漏 | DeerFlow |
| 过滤后继承 | 按规则挑一部分历史 | 灵活 | 规则难写 | OpenAI SDK（接力） |

算一笔账：主对话 8 万 token 时，全新上下文的子 Agent 起步约 5 千；分叉起步 8 万，就算命中缓存按一折算，每轮也相当于 8 千，子 Agent 跑几十轮累积不少。所以区别主要不在钱，而在“信息够不够”和“会不会被干扰”。

**我们的做法：全新上下文 + 自动附上用户原话。** 单纯全新上下文最大的风险是主 Agent 转述时丢了用户的真实意图；借 Codex 压缩时的观点——用户原话是需求唯一的来源——由 Runtime 自动把它附上：

```
[工具（按模式固定）][子 Agent 专用 system]
[环境信息]                                  ← 和主对话同一份
[背景：用户最近的原话（原样摘录，最多 2000 字，标明“仅供理解意图，任务以下面为准”）]
[任务：主 Agent 写的 prompt]
```

- **用户原话由 Runtime 摘录**，不经主 Agent 转述；从主账本里取本任务及之前的用户输入，从新到旧。
- **主 Agent 要把任务写全**：task 工具的说明里要求写清背景、要查或要做什么、要交回什么。
- **交回格式**：结论、证据（`文件:行号`）、不确定的地方，控制在 2000 字以内。派子 Agent 就是为了保护主上下文，交回几万字就没意义了。
- **缓存**：同一种模式的子 Agent，开头 `[工具][system][环境]` 逐字节相同，并行派出的几个之间能共享缓存前缀（从第二个起就能命中）。所以工具顺序、system、环境信息都要固定，用户原话和任务放在最后。

**两种模式分开看**：

| 模式 | 上下文 | 理由 |
|---|---|---|
| `explore`（只读查资料） | 全新 + 用户原话 | 这正是“上下文防火墙”的用法：查得再多，也只交回结论 |
| `general`（改代码） | 第一版同上；**以后可以加 `context="fork"` 选项** | 改代码往往需要知道主对话里已经做过的决定，比如“不能动某个接口”“已经排除了某种方案”，这种情况分叉更合适 |

第一版统一用“全新 + 用户原话”；等 `general` 真遇到“背景不够”的问题，再加分叉。分叉时要让子 Agent 的请求前缀和主对话逐字节相同，才能共享缓存（Claude Code 的做法）。

**结果怎么交回**：子 Agent 结束后，它最后的回答作为 task 的工具结果交回主 Agent，末尾附一行：状态、用了几步、多少 token、子账本的 id。子 Agent 没正常完成（预算用完、出错）也照样交回，写明状态，让主 Agent 决定怎么办。

**用量计入父任务**：工具结果事件 `ActionCompleted(kind=tool)` 可以带 `usage` 字段，`fold` 把它加进本任务的 token 计数。这是内核唯一的改动（一行）。这样派子 Agent 也受父任务预算约束，不会绕过预算。

**崩溃恢复**：task 调用中断了，按现有规则补一条“执行中断，结果未知”（子账本还在，以后可以做“续上旧的子 Agent”）。

**终端显示**：子 Agent 的每次工具调用显示成一行缩进的 `↳ [任务名] grep(...)`，不显示它的完整输出，免得刷屏。

**什么时候该派**（写进 system prompt）：需要大量搜索、读很多文件才能回答的问题，派 explore；彼此独立的几件事可以一次派多个并行；简单的一两次查找自己做，别派。

### 6. 暂不做

分叉（`general` 模式的 `context="fork"` 选项，见第 4 节）、后台子 Agent（派出去不等，完成后通知）、给运行中的子 Agent 追加指令、续上旧的子 Agent、团队协作、子 Agent 用别的（更便宜的）模型、git worktree 隔离。

## 三、测试

并行：

1. 分批：相邻只读并发、写操作独占、只读 bash 并发、写 bash 独占。
2. 真的并发了：3 个各睡 0.3 秒的只读调用，总耗时远小于 0.9 秒。
3. 按序写回：完成顺序和调用顺序相反时，投影里仍按调用顺序。
4. 一个出错不影响其他；调用和结果一一配对。
5. 崩溃在一批的中间（部分完成）：恢复后未完成的补错误，已完成的保留。
6. 前缀不变（缓存）。

子 Agent：

7. 结果交回：子 Agent 的最终回答成为工具结果；附状态、步数、token、子账本 id。
8. 子账本：独立一本，事件带 `parent_id`；不含记忆快照、含环境信息；背景里有用户原话（原样、从新到旧、有上限），任务在最后。
8b. 同一模式的两个子 Agent，请求开头 `[工具][system][环境]` 逐字节相同。
9. 工具集：explore 只有只读工具；general 有写工具；都没有 task、remember。
10. 用量计入父任务预算；子 Agent 自己超限时照样交回并写明状态。
11. 多个 explore 子 Agent 并行；general 独占。
12. 真实验证：问一个需要大量查找的问题（比如“这个项目的错误处理是怎么做的”），看主 Agent 是否派 explore 子 Agent、主上下文是否明显比自己查小。

## 进度（2026-10-01）

已实现：执行者分批并发（`Runner._do_all` / `_execute_batch`，线程池 + 账本加锁）；投影按调用顺序写回；工具声明 `parallel`、`wants_call_id`，工具可以返回附加信息（如 `usage`）；`weaver/subagent.py`（task 工具、explore / general、ExplorePolicy、子账本、用户原话摘录、用量计入父预算）；CLI 显示 `↳ [任务名] …`。测试见 `tests/test_parallel_subagent.py`。

真实验证 1（问“出错时怎么处理”，没要求派子 Agent）：模型没派，自己查，每轮并行发 3 个调用；主上下文涨到 2.2 万。它判断几轮能查完，不算错。

真实验证 2（明确要求派 4 个 explore）：4 个子 Agent 同时启动（相差 0.0 秒）、并行跑完用 92 秒（各自 71~92 秒，串行约 330 秒）；主会话输入只从 6.6k 涨到 14.5k（对比验证 1 的 2.2 万），上下文防火墙生效。

实测发现的问题：4 个子 Agent 和主任务全以 `budget` 结束。原因是 token 预算按“累计输入”算，缓存命中的部分也按全价——每轮重发整段上下文，子 Agent 第 10 轮输入 3 万、其中 2.8 万命中缓存，照样按 3 万扣，十几轮就过了 20 万；主任务再加上 4 个子 Agent 的用量也超了。改为按实际成本折算（`kernel.billable`）：没命中缓存的输入 + 命中缓存的输入 × 0.1 + 输出。

另外：同时派出的几个子 Agent，第一轮请求是同时发出的，彼此还来不及命中缓存（第二轮起才命中）；“兄弟之间共享前缀”要在先后派出时才明显。

复测（按实际成本折算之后）：4 个子 Agent 全部 `done`，各用 11~22 步、6.3 万~8.3 万（折算后）。主任务仍以 `budget` 结束：4 个子 Agent 合计约 30 万，超过主任务默认的 20 万（这个默认值是“缓存也按全价”时定的）。主任务默认预算改为 100 万（折算后，含子 Agent），子 Agent 各 20 万不变。超预算时收尾机制照常工作：主任务禁用工具再问一次模型，仍然交出了汇总表。

### 同时派出时的缓存预热（2026-10-01）

**问题**：同时派出的几个子 Agent，第一轮请求同时发出，共同前缀 `[工具][system][环境]` 还没进缓存，全都没命中，而且每个都写一遍缓存（Anthropic 写缓存要多收 25%）。

**做法**（`weaver/subagent.py` 的 `WarmGate`、`LeaderModel`）：同一种模式的一批子 Agent，第一个是“领头的”，先发请求；其余“跟随的”等领头的**收到第一个流式片段**再发——服务端开始输出时，输入已经处理完、缓存已经写好，这段等待一般只有 1~3 秒，不用等整轮回复。

- 领头的请求结束（成功或失败）也会放行，出错不会卡住别人；最多等 20 秒。
- 预热后 4 分钟内再派同一模式的子 Agent，直接跟随不用等（Anthropic 缓存默认 5 分钟）；超过就重新选领头的。
- explore、general 工具集不同、前缀不同，分开预热。

**值不值**：现在共同前缀约 3.5k，一批 4 个大约省 1 万 token（一两分钱），代价是跟随者多等 1~3 秒。收益不大，但以后做“分叉”（共同前缀可能 8 万）时就很值，机制先备好。

**真实验证**（同时派 3 个 explore 读文件第一行）：跟随者在 +1.9 秒发出第一轮请求（正是领头的开始输出的时候）；一个跟随者第一轮命中 2677；另一个仍没命中、重新写了一遍——OpenRouter 把它路由到了别的上游（各上游缓存不共享），和之前的路由问题是同一个原因，需要时用 `WEAVER_EXTRA_BODY` 固定上游。领头的这次也命中了，因为几分钟前跑过同样前缀的测试、缓存还没过期：`WarmGate` 只知道本进程里的预热，看不到服务端缓存，所以宁可保守多等一下。
