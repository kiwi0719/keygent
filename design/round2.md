# Weaver 第二轮：找回原文、记忆提取、后台任务、边生成边执行、子 Agent 进阶

草案 v1 · 2026-10-01

七件事，按“共用什么机制”分成五组：

| 组 | 包含 | 共用的机制 |
|---|---|---|
| 一、查账本 | 找回被压掉的原文、搜索历史会话 | 一个 `recall` 工具：账本里的原文一直都在 |
| 二、提取记忆 | 压缩前先提取、后台自动提取 | 同一个提取流程，只是触发时机不同 |
| 三、后台任务 | 长命令转后台、后台运行的子 Agent | “派出去不等，做完了通知”：任务登记表 + 完成通知 |
| 四、边生成边执行 | 模型还在输出时就开跑工具 | 只预执行只读工具，内核不改 |
| 五、子 Agent 进阶 | 分叉模式、自定义子 Agent 类型 | 子 Agent 的“上下文怎么来”和“身份怎么定”可配置 |

---

## 一、查账本：`recall` 工具

### 1. 要解决什么问题

- **压缩之后细节没了**：被裁剪的工具结果变成占位符，被摘要的对话只剩概括。模型有时恰好需要当初某个文件的原文、某条报错的全文。
- **过去的会话用不上**：“上周修过一个类似的 bug，当时怎么改的？”——那次会话的账本还在 `.weaver/sessions/` 里，但模型没法查。

### 2. 主流做法（第 7、10 课）

“原文不删，只移出上下文，需要时能找回”是压缩的新趋势：Deep Agents 把压掉的历史存成文件、Hermes 用 `session_search` 查数据库、Claude Code 在摘要里附完整记录路径、OpenHands 的视图每次从事件日志重建。搜历史会话：Hermes（FTS5 全文检索）、DeepSeek Harness（5 个 session 工具）、OpenClaw（`memory_search`）。

### 3. 我们的做法

我们有天然优势：**账本里原文一直都在**（只追加、不删；而且进账本前已经脱敏），压缩只影响投影。所以只要一个工具：

```
recall(query="", scope="session", session="", seq=0)
  query   关键字，多个词空格分开，都要出现
  scope   session：只搜当前会话（含被压缩掉的部分）；all：搜这个项目的所有会话
  seq     直接取某一条记录的原文（配合下面的占位符用）
```

- **搜索**：读账本，搜用户的话、模型的回复、工具结果的文字；按“都包含所有关键字”过滤，新的排前面，最多 10 条，每条给会话 id、时间、序号、前后一段摘录（最多 500 字）。子 Agent 的账本也搜，标明是子 Agent。第一版直接扫 JSONL 文件；会话多到慢了再加 SQLite 全文索引（Hermes 的做法）。
- **取原文**：`recall(seq=123)` 返回那一条的完整内容（太长截到 30KB 并说明）；`session` 不填就是当前会话。
- **占位符带上序号**：裁剪后的占位符从“[旧工具结果已清理，需要时请重新读取]”改成“[旧工具结果已清理（#123），需要时重新读取，或用 recall(seq=123) 取回原文]”。摘要开头也加一句“完整记录在账本里，可以用 recall 查”。占位符是确定的，缓存不受影响。
- 只读，放行，可以并行；explore 子 Agent 也给。

## 二、提取记忆

### 1. 要解决什么问题

现在的记忆只有“模型当场用 remember 写”一种来源，模型专心干活时常常忘了记。压缩更糟：被摘要掉的对话里可能有用户说过的偏好，摘要不一定留得住。

### 2. 主流做法（第 10 课“谁来写”）

| 项目 | 触发时机 | 做法 |
|---|---|---|
| Claude Code | 每轮结束 | 分叉子 Agent 提取；**主模型这一轮已写过则跳过** |
| Hermes | 每 10 轮 | 后台复查 |
| DeerFlow | 对话后防抖 30 秒 | 模型提取带置信度的事实，≥ 0.7 才存 |
| **OpenClaw** | **压缩之前** | 静默跑一轮，只能追加到当日日志 |
| Codex | 新一轮输入时 | 处理闲置超 6 小时的旧会话 |
| OpenAI SDK | 会话关闭时 | 小模型逐个提取，大模型整合 |

### 3. 我们的做法：一个提取流程，两个时机

**提取流程**（`weaver/extract.py`）：

- 发给模型：**和最近一次请求完全相同的前缀**（同样的 system、同样的工具清单、同样的对话）+ 一条提取要求。前缀相同，几乎全部命中缓存，很便宜——这是压缩写摘要时用过的招（DeepSeek Harness 的做法）。
- 提取要求：按记忆的四类（user / feedback / project / reference）找出“以后的会话也用得上、代码里查不到”的东西，用 `remember` 写；先看已有的记忆索引，相近的就覆盖同名记忆；没有值得记的就直接说“没有”。
- **只允许调用 `remember` / `forget`**：工具清单不能改（改了前缀就不同了），所以靠执行时拦——别的工具一律补“提取阶段只能用 remember”的错误结果。最多 3 轮。
- 写入照样过记忆模块的检查（密钥、注入、大小）。
- 记进账本：一条 `ActionStarted / ActionCompleted(kind="extract")`，输出里记下存了哪几条、用量（计入预算）。内核不认识这个 kind，只当记录，不影响决策。

**两个时机**：

| 时机 | 条件 | 说明 |
|---|---|---|
| **压缩之前** | 这次压缩是写摘要（裁剪不会丢对话，不用） | OpenClaw 的做法：反正要把旧内容移出去，先把值得长期留的捞出来 |
| **任务结束后** | 这个任务跑了 ≥ 3 步，且**这个任务里模型没调用过 remember** | Claude Code 的“写过就跳过”；短任务通常没什么可记 |

- 可以关：`WEAVER_MEMORY_EXTRACT=0`。
- 子 Agent 不提取（它的上下文是派活时拼的，不是和用户的真实对话）。
- 终端显示一行：“记忆提取：存了 2 条（prefer-pnpm、deploy-doc）”或“没有新的记忆”。

“后台”在 CLI 里的意思是：任务结束、答案已经显示之后再跑，用户能看到结果，不用等它；以后有了常驻的服务器版执行者，就能真正在后台跑。

## 三、后台任务：长命令和后台子 Agent

### 1. 要解决什么问题

- **长命令**：启动开发服务器（`npm run dev`）、跑很久的测试、`tail -f` 日志。现在 bash 前台执行，开发服务器永远不会“结束”，只能等 120 秒超时被杀。
- **后台子 Agent**：派一个子 Agent 去跑很久的事（比如完整的测试回归），主 Agent 想在这期间继续做别的。

### 2. 主流做法（第 4、16 课）

- 长命令：Claude Code 的 Bash 有 `run_in_background`，之后用工具读输出、杀进程；Codex 的 `exec_command` 等满 10 秒还没结束就先交回会话 id，之后用 `write_stdin` 读后续输出。
- 后台子 Agent：Claude Code（`<task-notification>` 通知）、Codex（`wait_agent` 主动等）、Hermes、DeepSeek Harness。

### 3. 我们的做法：任务登记表 + 完成通知

**任务登记表**（`weaver/jobs.py`）：进程内的一张表，记每个后台任务：id、类型（shell / agent）、说明、状态（running / done / failed / killed）、开始时间、退出码或结论、输出文件。

**长命令**：

```
bash(command, background=true)
  → 立刻启动（同样在沙箱里、同样去掉密钥环境变量），输出写到 .weaver/jobs/<id>.log
  → 等 3 秒，把这 3 秒的输出和任务 id 一起返回（启动失败、端口占用这类问题通常 3 秒内就看得出来）
job_output(id, tail=200)   读新输出（从上次读到的位置开始；脱敏后返回）
job_kill(id)               结束任务（连同子进程）
jobs()                     列出所有后台任务和状态
```

- 权限、沙箱和前台 bash 一样（后台跑的是同一条命令）。
- **Weaver 进程退出时，后台的 shell 任务一并结束**（开发服务器跟着 Weaver 走），启动时说明这一点。

**后台子 Agent**：

```
task(description, prompt, mode, background=true)
  → 立刻返回“已派出，任务 id X”，子 Agent 在线程里跑
job_wait(id, timeout=60)   需要结果时主动等（Codex 的 wait_agent）
```

**完成通知**（Claude Code 的 task-notification）：后台任务结束时，执行者在下一个决策点往账本追加一条 `InputReceived(source="system")`：“后台任务 X（npm test）结束了，退出码 1，最后几行输出：…” / “后台子 Agent X（查错误处理）完成，汇报：…”。

- `system` 来源本来就会被直接接受，所以：**主任务还在跑**，通知就像插话一样排进对话；**主任务已经结束**，通知会开启一个新任务，主 Agent 被“叫醒”来处理结果——这正是常驻 Agent 需要的行为。
- CLI 里：主任务结束后，如果还有后台子 Agent 在跑，等它们（显示“等待 2 个后台任务…”，Ctrl+C 可以不等）；后台 shell 任务不等。

内核不用改：通知就是一条输入。

### 4. 资源与泄漏（实测 + 防护）

实测（2026-10-01）：Weaver 自身模块加载后约 32 MB；4 个子 Agent 并行各 20 步，堆峰值 5.2 MB、结束后剩 0.3 MB，线程和文件描述符回到原数；MCP SDK 导入 +38 MB，连接开关 10 次堆内存基本不变（3.22 → 3.24 MB）、无残留进程。**后台程序本身（开发服务器常常几百 MB）是独立进程，不算在 Weaver 里。**

后台任务的风险不在堆内存，在“进程和句柄”：

| 风险 | 后果 | 防护 |
|---|---|---|
| 孤儿进程 | Weaver 被强杀或崩溃，退出时的清理没跑，开发服务器一直占着端口 | 后台进程的 PID 和启动命令记到 `.weaver/jobs/registry.json`；**下次启动时检查上次残留的**，列出来问要不要清理（Linux 能让子进程随父进程死，macOS 没有，只能靠登记） |
| 僵尸进程 | 结束了没人回收，占进程表 | 查状态时回收 + 一个后台回收线程 |
| 句柄没关 | 长时间运行后“打开文件太多” | 输出写文件不走管道（也避免“管道满了进程卡住”）；任务结束立刻关句柄；登记表只留元信息，最多留最近 100 条 |
| 日志无限增长 | 撑满磁盘 | 每个任务日志上限 10 MB，超过只保留后一半 |
| 后台子 Agent 卡住 | 线程永远占着 | 各层已有超时（模型 300 秒、步数上限）；线程设为随进程退出 |
| 预执行结果没人取 | 堆积 | 每条模型回复处理完就清空 |

### 5. 顺带发现的现有问题：账本每次追加都整本重读

`Runner._append` 每次写账本前都 `load` 整本账本取当前序号。实测 5000 条、10 MB 的账本读一次 40 ms，长会话里累积起来接近平方增长，越到后面每一步越慢（不是内存泄漏，读完就释放）。改法：账本存储记住“当前条数 + 文件长度”，追加时只读新增的部分（单写者，安全）。放在第二轮最前面修。

**已修（2026-10-01）**。模拟长会话（每步一次模型调用 + 一次工具调用，工具结果 2KB，假模型不耗时）：

| | 1000 步总用时 | 第 800~1000 步每步 | 3000 步 |
|---|---|---|---|
| 修之前 | 74 秒 | 140 ms | —（太慢没跑） |
| 只改存储（读新增部分） | 6.2 秒 | 12 ms | — |
| 再改 fold（接着上次算） | **1.3 秒** | **1.7 ms** | 10 秒，最后每步 6.5 ms |

1. **存储只读新增部分**（`JsonlEventStore`）：记住每个文件读到的字节位置和已解析的事件；文件被换掉（inode 变了）或变短就从头读；自己写的直接加进缓存。
2. **剖析后发现第二个热点**：存储改完还在线性变慢，用 cProfile 一看，14 秒里 12 秒在 `fold`——每次决策前都从头重算状态，而且防死循环那里每条工具结果要做一次 JSON 序列化。改成**可以接着算**：`fold(events, 上次的状态)` 只处理新增的事件。fold 本来就是逐条处理、不往回看，所以“一次算完”和“分段接着算”结果完全一样（测试在每个切分点比对）；账本被换掉（变短、或接续点的 id 对不上）就从头算。内核仍然是纯函数。
3. **顺手修的现存 bug**：进程在写账本时崩溃会在末尾留下半行；以前下一次追加会接在半行后面，把它变成文件中间的坏行，之后新开的进程读到它就停，**它后面的记录全丢**。现在追加前先把读到的位置之后的内容挪进备份文件（`<会话>.jsonl.corrupt-<时间>`，不真删），再截掉。

剩下的线性部分主要是每次调模型时重建要发出去的对话（`project`）——请求本来就要带上全部消息，这部分省不掉；3000 步时每步 6.5 ms，和模型调用的几秒比可以忽略。

## 四、边生成边执行

### 1. 要解决什么问题

模型一次回复里先说几句话、再发 3 个调用，要等整条回复生成完才开始执行第一个。Claude Code、Codex 不等：一个调用的参数一完整就开跑，执行和生成重叠，省掉几秒。

### 2. 难点

我们的内核是“模型回复记进账本 → 决定下一步 → 执行”。如果在回复记进账本之前就执行，账本顺序就乱了，崩溃恢复也难（工具执行了一半、模型回复却没记下来）。

### 3. 我们的做法：只**预执行只读工具**，内核不改

- 流式解析时，一个工具调用的参数一完整（Anthropic 的 `content_block_stop`；OpenAI 是下一个调用开始或回复结束），执行者检查：**这个工具能并行（只读）、权限是放行**——两个条件都满足就在线程里先跑，结果暂存（按调用 id 和参数）。
- 回复完整后照常记账本、照常让内核决定；轮到执行这个调用时，**参数一样就直接用暂存的结果**，不一样（极少见）就重新执行。账本里的顺序和现在完全一样。
- 只读工具没有副作用，预执行的结果就算最后没用上（比如回复被截断、调用被内核拒绝），扔掉也没关系。写文件、跑命令、要审批的一律不预执行。
- 收益：长回复里的 grep / read_file 能和生成重叠；子 Agent、MCP 只读工具同样受益。可以关：`WEAVER_EAGER_TOOLS=0`。

## 五、子 Agent 进阶

### 1. 分叉模式（`general` 的 `context="fork"`）

**要解决什么问题**：parallel-subagent.md 里定过——改代码的子 Agent 往往需要主对话里已经做过的决定（“不能动某个接口”“已经排除了某种方案”），全新上下文 + 用户原话不够。

**主流做法**：Claude Code、Codex V2、OpenClaw 支持分叉：子 Agent 继承主对话历史。Claude Code 让同一批分叉的子 Agent 请求前缀逐字节相同，共享缓存。

**我们的做法**：

- `task(..., mode="general", context="fork")`。
- **前缀和主对话逐字节相同**才能共享缓存，所以分叉的子 Agent：
  - 用**主 Agent 的 system prompt 和工具清单**（不用子 Agent 的精简版）；不允许的工具（task、remember 等）不从清单里删，而是**执行时拒绝**（删了前缀就不同了）。
  - 对话 = 主对话投影到“发出这个 task 调用的那条模型回复之前” + 一条新的用户消息：“你是分叉出来的子 Agent，看得到上面的完整对话。现在只做这件事：…；做完用一段话汇报”。
- **账本**：子账本第一条是 `InputReceived(source="context", context_kind="fork", parent=<父会话>, upto=<序号>)`；投影遇到它，就把父会话投影到那个位置的消息原样展开。父账本只追加不改，所以展开结果永远一样。
- 分叉不能再分叉；只给 general（explore 用全新上下文就够了，隔离更好）。

代价：子 Agent 背着整段历史，主对话很长时每轮都要读一大段缓存（按一折算）；适合“改代码需要知道前情”的场景，不是默认。

### 2. 自定义子 Agent 类型（`.weaver/agents/*.md`）

**主流做法**：Claude Code `.claude/agents/*.md`、OpenHands `.agents/agents/*.md`：一个 Markdown 文件定义一种子 Agent——frontmatter 写名字、描述、能用哪些工具，正文就是它的 system prompt。

**我们的做法**：

```markdown
---
name: test-runner
description: 跑测试、分析失败原因，不改代码
tools: read_file, grep, find_files, bash
---
你是测试专员。先跑完整测试……（这就是它的 system prompt）
```

- 目录：`.weaver/agents/`、`.claude/agents/`（项目级，要先信任，和 skills 一样）、`~/.weaver/agents/`、`~/.claude/agents/`（用户级）。
- `tools` 不写就是 general 的全部工具；Claude Code 的工具名自动对应（Read→read_file、Grep→grep、Glob→find_files、Bash→bash、Edit→edit_file、Write→write_file）；不认识的忽略。工具全是只读的，这个类型就能并行。
- 用法：`task(description, prompt, agent="test-runner")`。可用的类型作为背景信息（`kind="agents"`）列给主 Agent，不写进 task 工具的说明（写进去会改工具清单，破坏缓存）。
- 还是深度 1：自定义类型里写了 task 也会被去掉。

## 六、内核改动

几乎没有：

| 改动 | 原因 |
|---|---|
| 投影：裁剪占位符带上序号 | recall 取原文 |
| 投影：遇到 `context_kind="fork"` 展开父会话的消息（需要能读父账本） | 分叉 |
| `ActionCompleted(kind="extract")` 只是记录，`fold` 忽略 | 记忆提取 |

后台任务的通知、预执行都在执行者里；子 Agent 类型、recall 是工具。

## 七、建议的顺序

| 顺序 | 内容 | 理由 |
|---|---|---|
| 0 | ~~修账本整本重读~~（已完成） | 现有的性能问题，长会话越来越慢 |
| 1 | recall（查账本） | 最简单、最实用；压缩和记忆都要用它兜底 |
| 2 | 后台任务（长命令 + 通知） | 开发服务器是编码 Agent 的刚需 |
| 3 | 记忆提取（压缩前 + 任务结束后） | 记忆系统从“靠模型自觉”变成“自动积累” |
| 4 | 自定义子 Agent 类型 | 小，复用 skills 的发现和信任 |
| 5 | 后台子 Agent | 复用第 2 步的登记表和通知 |
| 6 | 分叉模式 | 要动投影，最复杂 |
| 7 | 边生成边执行 | 收益是几秒延迟，放最后 |

## 八、测试要点

- recall：搜当前会话（含被压缩的部分）、搜所有会话、取原文、占位符带序号、太长截断、子 Agent 账本标明。
- 提取：前缀和最近一次请求相同；只允许 remember；任务里调过 remember 就跳过；短任务不提取；压缩写摘要前提取、裁剪不提取；计入预算；可以关。
- 后台任务：后台启动立刻返回、3 秒输出、读新输出、杀掉（连子进程）、完成通知（任务进行中 / 已结束两种）、进程退出时清理、后台子 Agent 和 job_wait。
- 预执行：只读且放行的才预执行；结果复用；参数不同重新执行；回复被截断时丢弃；账本顺序不变。
- 分叉：子 Agent 第一轮请求的前缀和主对话逐字节相同；不允许的工具执行时拒绝；父账本之后再追加不影响子 Agent 的投影。
- 自定义类型：发现、信任、工具对应、只读类型可并行、深度 1。
