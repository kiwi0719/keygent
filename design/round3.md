## 一、记忆自动提取

### 1. 沿用 round2.md 的部分

- 一个提取流程（`weaver/extract.py`），两个时机：**压缩写摘要之前**、**任务结束后**。
- 发给模型的前缀和最近一次请求逐字节相同，再加一条提取要求，几乎全部命中缓存，很便宜。
- 只允许 `remember` / `forget`。工具清单不改（改了缓存就失效），别的工具在执行时拦下。最多 3 轮。
- 跳过的情况：这一轮少于 3 步；这一轮里模型自己调过 `remember`；子 Agent 不提取。
- 账本记一条 `ActionCompleted(kind="extract")`，内核忽略它。步骤里显示成“记住了 2 条”或“没有新的记忆”（步骤翻译已经支持）。
- 默认开启，`WEAVER_MEMORY_EXTRACT=0` 关闭。

### 2. 常驻服务里的新问题和决定

**① 临时目录里的任务没有“项目”**

没指定工作目录的任务跑在 `~/Weaver/scratch/<任务 id>/`，每个任务一个新目录。项目级记忆写在那里，下一个任务就看不到了，等于白记。

决定：工作目录在 scratch 下面的任务**没有项目层**。
- `remember` 只能写用户级；`scope=project` 自动改成 user，并在结果里说明。
- 快照里不列项目级记忆索引。
- 提取要求里告诉模型“这个任务没有项目，只记跟用户本人有关的”。

**② 任务结束后在哪里提取**

在工作线程里做：`run()` 跑完，这一轮是 `done`（出错、取消、预算用完的不提取，信息多半不完整），而且没有新的输入在排队，就接着提取，然后再睡。

- 提取期间任务状态照样显示“完成”（提取不算新的一轮）。
- 用户这时候插话：等提取做完（通常几秒）再开始新的一轮。不打断提取，免得记一半。

**③ 两个任务同时写记忆**

现在最多 4 个任务同时跑，可能同时往用户级记忆写同名文件、同时重建索引 `MEMORY.md`。

决定：记忆目录加一把**文件锁**（`fcntl.flock`，锁 `memory/.lock`）。写记忆和重建索引都在锁里做；命令行和 weaverd 同时写也安全。

**④ 记忆变了，正在跑的任务看不看得到**

沿用现有机制：快照在一轮开始时冻结，变了就在下一轮开始前追加新快照，不改已发出的前缀。所以 A 任务刚记住的东西，B 任务要到下一轮才看到。这是有意的，为了保住缓存。

**⑤ 花多少钱**

提取的用量记在 `extract` 记录里，**不算进这一轮的预算**（这一轮已经结束了），算进任务的累计用量（详情接口的 `usage` 加一项 `extract_tokens`）。因为前缀命中缓存，一次提取大约是正常一步的十分之一到五分之一。

### 3. 已定（2026-10-01）

- 只在这一轮 `done` 时提取；出错、取消、预算用完的不提取（对话里常有“这样不行”的半成品结论，容易记错）。

## 二、子 Agent 进阶

三件事：自定义类型、后台子 Agent、分叉。建议按这个顺序做，前一件是后一件的基础。

### 1. 自定义子 Agent 类型（`.weaver/agents/*.md`）

沿用 round2.md 第五节第 2 小节：一个 Markdown 文件定义一种子 Agent。frontmatter 写名字、描述、能用的工具，正文就是它的 system prompt；兼容 `.claude/agents/`；Claude Code 的工具名自动对应。

新增的决定：

- **可以指定模型**：frontmatter 里写 `model: claude-haiku-4.5`，同一个服务商换个模型名。查资料这类简单活用便宜的模型。不写就用主模型。Claude Code 也支持这个。
- **常驻服务里的信任**：项目级的类型（以及项目级 skill）是别人写的指令，要先信任。现在常驻服务里没有入口确认，只能先在命令行确认一次。
  新增一种等待 `kind="trust"`：任务第一次用到某个未信任项目的类型 / skill 时，记一件“等你的事”：“项目 X 里有 2 个子 Agent 类型、3 个 skill，信任吗？”。选项 `allow` / `deny`，确认结果和命令行共用同一份信任记录。
  Keygent 要能显示这种等待（按 api.md 的约定，不认识的 `kind` 也能按 `choices` 出按钮，所以不改也能用）。
- 可用的类型作为背景信息列给主 Agent，不写进 task 工具的说明（写进去会改工具清单、破坏缓存）。
- 深度还是 1：子 Agent 不能再派子 Agent。

### 2. 后台子 Agent

`task(..., background=true)`：立刻返回“已派出，后台任务 X”，子 Agent 在后台跑，主 Agent 接着干别的；做完时用和后台命令一样的通知叫醒主任务：“后台子 Agent X（查错误处理）完成了，汇报：…”。

**复用后台命令的登记表**（`weaver/jobs.py`），登记表里多一种类型 `agent`：

| | 后台命令 | 后台子 Agent |
|---|---|---|
| 启动 | 子进程 | 线程里跑一个子执行者（子账本照常写） |
| `job_output(id)` | 新输出 | 进度：已经走了几步、当前在做什么（最后一个步骤的标题） |
| `job_wait(id, timeout)` | — | 新增：主 Agent 需要结果时主动等，最多等 timeout 秒；等到了就返回汇报 |
| `job_kill(id)` | 结束进程组 | 取消子执行者（它正在跑的命令一起打断） |
| 结束通知 | 退出码 + 最后几行输出 | 汇报（最多 8KB，完整的在子账本里） |

决定：

- **只允许只读的子 Agent 在后台跑**：explore，以及工具全是只读的自定义类型。能改文件的（general）在后台和主 Agent 同时改同一批文件，会互相覆盖，第一版不允许。要的话以后加“各自在 git worktree 里改”。
- **数量**：每个任务同时最多 3 个后台子 Agent，多的直接报错，让模型等一等。它们不占任务管理器那 4 个名额（属于任务内部），但都算进这个任务的预算。
- **审批**：只读的子 Agent 基本不需要审批（读敏感文件除外）；需要时和现在一样直接拒绝，让它在汇报里说明。
- **主任务被取消**：它派出的后台子 Agent 一起取消。理由：用户点“取消”是想让这件事全部停下。**主任务结束**（done）时不取消：后台子 Agent 就是为了“主任务先答复，结果晚点到”。
- **weaverd 重启**：线程没了，但子账本还在。第一版把它标成“中断”，并通知主任务：“后台子 Agent X 因为 weaverd 重启中断了，已经做了 N 步”。以后可以照着子账本接着跑（内核本来就能从账本恢复）。
- **命令行模式**：主任务结束时如果还有后台子 Agent 在跑，等它们（显示“等待 2 个后台子 Agent…”，Ctrl+C 不等）。

**接口**：任务详情多一个 `jobs` 字段，列出这个任务的后台命令和后台子 Agent（id、类型、标题、状态、开始时间），Keygent 可以显示“后台还在跑什么”。这是 api.md 的新增字段，旧版 Keygent 忽略即可。

### 3. 分叉（`general` 的 `context="fork"`）

沿用 round2.md 第五节第 1 小节：子 Agent 继承主对话历史。前缀和主对话逐字节相同，可以共享缓存；不允许的工具不从清单删，在执行时拒绝；子账本第一条记“从父账本第几条分叉”，投影时展开父账本到那个位置。

新增的决定：

- **只在前台**：分叉的是 general，会改文件，按上一条的规矩不能放后台。
- **前缀要和主对话的最近一次请求完全一样**：包括背景信息快照（环境、记忆、skills）。所以分叉的子 Agent 不另外放自己的背景信息，直接用父账本里的。
- **审批**：分叉的子 Agent 能改文件、跑命令，比 explore 更常需要审批。常驻服务里“直接拒绝”太死板了。
  决定：**子 Agent 的审批升到主任务的“等你的事”里**。等待里带上“来自子 Agent：X”，你放行后子 Agent 接着跑。
  这要求子执行者在等待时不退出，而是挂起等回答。做法：子执行者的 approver 改成“在父任务里记一件等待，然后阻塞等它被回答”；父任务的工作线程此时正卡在 `task` 这个工具调用里，所以不会冲突。
  这个机制对普通的前台 general 子 Agent 也一样适用，顺带解决“常驻服务里子 Agent 不能要审批”的老问题。
- 分叉不能再分叉。

### 4. 已定（2026-10-01）

- 后台子 Agent 第一版只允许只读的；能改文件的以后配合 git worktree 再做。
- 子 Agent 的审批升到主任务的“等你的事”里，带“来自子 Agent：X”。

## 三、跨任务搜索

### 1. 要解决什么问题

“上周那个流失分析里，华北的阈值最后定的多少？”“之前修过一个类似的报错，当时怎么改的？” 现在 `recall` 只能查当前任务，别的任务的账本都在 `~/.weaver/tasks/` 里，模型却查不到。

### 2. 做法

**`recall` 加一个范围参数**：

```
recall(query, scope="task")     只查当前任务（现在的行为，默认）
recall(query, scope="all")      查所有任务（常驻服务：~/.weaver/tasks/；命令行：这个项目的 .weaver/sessions/）
recall(task="a1b2c3", seq=12)   取别的任务某一条的原文
```

- 结果每条带上任务标题、任务 id、日期、序号、前后一段摘录：“[Q3 流失分析 · 9 月 24 日 · a1b2c3 #57] …华北阈值改成 60 天…”。最多 10 条，新的在前。
- 搜的内容和现在一样：用户的话、模型的回复、工具结果、压缩摘要；不搜背景信息。子 Agent 的账本也搜，标明“子 Agent”。
- **归档的任务默认不搜**：归档就是“不想再看到了”。`scope="all"` 加 `archived=true` 才搜。
- 常驻服务里，**项目相关的任务优先**：工作目录和当前任务相同的排在前面。

### 3. 怎么搜得快

任务多了以后，每次都把所有账本读一遍会慢。粗算：100 个任务、每个 2 MB，全部扫一遍大约 1 秒。

**第一版：直接扫 + 缓存**

- 每本账本抽出“可搜的文字”（每条记录一段）放在内存里，按（文件、大小、修改时间）缓存；账本只追加，所以只需要接着读新增的部分（和账本的增量读取一样）。
- 查询就是在这些文字里做“都包含这几个关键字”的子串匹配。中文按子串匹配，不需要分词。
- 内存上限 200 MB（大约 1–2 万本账本的文字量），超了就按最久没用的丢掉，下次用到再读。

**以后：SQLite 全文索引**

- 任务到几千个以后再做。标准库自带 SQLite，FTS5 的 `trigram` 分词器能做中文子串搜索，但**少于 3 个字的词搜不了**（比如“华北”）。所以就算用了索引，两个字的关键词也还要退回扫描。
- 正因为有这个限制，第一版不上索引。

### 4. 安全

别的任务的内容会进到当前任务的上下文里。账本进账本前已经脱敏，内容也都是你自己的，所以问题不大。

要注意的一点：别的任务里可能有从网上抓来的内容，里面可能带着“忽略之前的指令”这类话。处理和读文件一样，作为工具结果交给模型，不当成指令。

### 5. 顺带：给 Keygent 的搜索接口

`GET /v1/search?q=华北 阈值` 返回同样的结果（任务、序号、摘录），Keygent 可以做一个搜索框，点结果跳到那个任务的那一步。复用同一套搜索。**已定：加。**

## 四、内核改动

| 改动 | 原因 |
|---|---|
| 投影：遇到 `context_kind="fork"` 展开父账本到指定位置 | 分叉 |
| 新的等待 `kind="trust"`（一个 `input` 类的等待，不和工具调用绑定） | 常驻服务里信任项目级类型 / skill |

其余（提取、后台子 Agent、子 Agent 审批升级、跨任务搜索）都在执行者、工具、任务管理器里，内核不动。

| 顺序 | 内容 | 理由 |
|---|---|---|

## 六、测试要点

- 提取：前缀和最近一次请求逐字节相同；只允许 remember；调过 remember 就跳过；短任务不提取；只在 done 后提取；压缩写摘要前提取、裁剪不提取；scratch 任务只写用户级；两个线程同时写记忆不坏索引；提取期间插话，等提取完再开始新一轮；可以关。
- 跨任务：搜到别的任务、标题和日期正确；归档的默认不搜；同一工作目录的排前面；增量缓存（账本追加后能搜到新内容、不重读旧的）；取别的任务的原文。
- 子 Agent 审批：子 Agent 要审批 → 主任务出现“来自子 Agent”的等待 → 放行后子 Agent 接着跑；拒绝；主任务取消时子 Agent 的等待作废。
- 自定义类型：发现、信任等待、工具对应、指定模型、只读类型可以后台和并行、深度 1。
- 后台子 Agent：立刻返回、job_output 看进度、job_wait 等结果、完成通知叫醒主任务、主任务取消时一起取消、done 时不取消、重启后标成中断并通知、每个任务最多 3 个、能改文件的不允许后台。
- 分叉：第一轮请求的前缀和主对话逐字节相同；不允许的工具执行时拒绝；父账本之后追加不影响子 Agent 的投影；不能再分叉。

内核改动：`fold` 忽略 `kind=extract`；一轮结束时子 Agent 升上来的等待一起作废。另外 task 工具一次加齐了 `agent`、`background`、`context` 三个参数，工具清单以后不会再因为这几项变。

**实现中发现并修掉的问题**：

1. 子 Agent 等审批时取消主任务，子 Agent 永远挂着：`Runner.cancel` 记的取消不带 run_id，`ask_up` 按 run_id 匹配就看不到。改成：等待开始之后出现的任何取消都算。
2. `ask_up` 先记等待、再记“从哪里开始看”，回答来得快就会漏掉。改成先记位置再记等待。
3. 同时派出 4 个后台子 Agent，数量检查和登记不在一起做，4 个都通过了检查。改成在同一把锁里数和登记。
4. Claude Code 类型文件里写的 `Task` 没对应到 `task`，深度 1 的限制被绕过。已补上对应。

**真实验证（OpenRouter，claude-sonnet-4.5，临时 WEAVER_HOME）**：

1. 项目里放了一个 `reviewer` 类型：任务开始时出现“信任项目 proj 里的 skill 和子 Agent 类型吗？”，放行；说“我习惯用 pnpm”，模型当场 `remember` 了 `prefer-pnpm`（用户级），所以这一轮按规则跳过提取。
2. 新任务（临时目录）：“之前那个任务里 build 脚本是什么”。模型先查了本任务没查到，换 `scope=all` 后找到了：“build 脚本是 vite build”。
3. `agent=reviewer` 审查 calc.py：用的是 reviewer 的说明和只读工具。
4. 后台 explore 子 Agent + `job_wait`：派出、等到结果，回答“calc.py 中定义了 1 个函数”。
5. general 子 Agent 要跑 `python3 -c "import calc; …"`：主任务的“等你的事”里出现“来自子 Agent：执行 Python 导入测试”，放行后输出 5。
6. 分叉：子 Agent 给 `add` 加上了 `int` 类型注解；它想 `pip3 install mypy`，审批升了上来（测试脚本自动放行了），被沙箱拦下，没有装进系统。

**观察到的成本**：短任务里，一轮结束后的提取约 3.5k–4.6k token（折算后），相当于这个任务的 20%–40%，比设计时估的“正常一步的十分之一到五分之一”贵。原因是短任务本身步数少，而提取要把整段对话（命中缓存的按一折）再读一遍，再加上模型的输出。可以考虑把“至少 3 步”提高，或者只在对话里出现了用户的偏好、纠正时才提取，等你决定。
