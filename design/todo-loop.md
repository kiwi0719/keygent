# Weaver todo 清单与防死循环设计

草案 v1 · 2026-10-01

两件事都在解决“长任务跑偏”：todo 管“做到哪了、别忘了还有什么”，防死循环管“别在一个地方打转”。它们共用同一个机制——**内核在合适的时候往对话末尾插一条提醒**，所以放在一起设计。

---

## 一、todo 清单

### 1. 要解决什么问题

任务一长，模型容易忘了还有几步没做，或者做到一半就说“完成了”。todo 清单给它一张纸：开工前把任务拆成几步写下来，边做边勾。

### 2. 主流做法（main.md 第 12 课）

- **结构已经收敛**：内容 + 三到四种状态（pending / in_progress / completed，有的多一个 cancelled），**模型自己写、自己更新**。这是“把规划交给模型”的典型：内核只提供一张纸。
- **内核在三处补位，防跑偏**：
  - 定期强制规划（smolagents）
  - **todo 太久没更新就插提醒**（Claude Code：10 轮没更新）
  - **压缩后 todo 不见了就补回去**（DeerFlow）
- 防“提前收工”（清单没做完就想停）是第 13 课“完成判定”的内容，我们正好有 `on_model_done` 这个接口，顺手做一个最简单的。

计划模式（先想后做、想的时候不许改）是另一个层次，这次不做。

### 3. 我们的做法

**工具**（沿用 Claude Code 的 `TodoWrite` 写法：每次提交整张清单，不做增删改的小操作，最不容易出错）：

```
todo_write(todos: [{content, status}])
  status: pending / in_progress / completed / cancelled
```

- 同一时刻**最多一项** `in_progress`，多了返回错误让模型改（聚焦当前这一步）。
- 返回渲染好的清单，终端上也显示成勾选框。
- 什么时候用写进工具说明：三步以上的任务开工前先写；每做完一步就更新；简单的一两步任务别用。

**清单存在哪：账本里，不另存**（Pi 的示例扩展、第 32 课的 mini_agent 都是这样）：当前清单 = 账本里最近一次成功的 `todo_write` 调用的参数。好处是崩溃恢复、`-s` 接着跑都天然正确，不用维护第二份状态。

**内核的三处补位**：

| 情况 | 做法 |
|---|---|
| 清单里还有没做完的，而且 **10 步没更新过** | 插一条提醒：“清单 N 步没更新了，这是当前清单：…，完成了的请勾上，计划变了请改” |
| **压缩之后**清单里还有没做完的 | 插一条提醒，把当前清单补回来（压缩可能把之前的 todo_write 压进了摘要） |
| 模型说“做完了”，但清单里还有 pending / in_progress 的 | 打回一次：“清单里还有这几项没完成：…。确实做完了就更新清单；不做了就标 cancelled 并说明原因”。**同一张清单只打回一次**，模型坚持就放行，免得死循环 |

子 Agent 不给 todo_write（子任务本来就短）。

## 二、防死循环

### 1. 要解决什么问题

模型有时会在原地打转：反复跑同一条失败的命令、反复读同一个文件、在两个动作之间来回摇摆。步数上限最终能拦住，但要白白烧掉几十步。

### 2. 主流做法（main.md 第 14 课）

三类刹车：步数上限、预算上限（我们都有）、**死循环检测**。死循环检测正在“从次数走向模式”：

| 项目 | 做法 |
|---|---|
| OpenHands | 卡死检测器（默认开）：同一动作和结果重复 4 次、同一错误连报 4 次、自言自语、两个动作来回摇摆 6 次，判定后停下 |
| Hermes | 三种计数：同一调用失败、同一工具换参数仍失败、只读工具反复无进展；先提醒 2~3 次，再硬停 5~8 次（有人值守时默认不硬停） |
| DeepSeek Harness | 同一调用连续重复 3 / 5 / 8 次时提醒，不拦截 |
| OpenCode | 同一调用重复时强制审批 |

共识：**先提醒、给模型机会换思路，再不行才停**；重复次数本身不代表卡住，要看结果是不是也一样（有进展的重复是正常的，比如轮询构建状态）。

### 3. 我们的做法

**识别四种模式**（只看当前任务里最近的工具调用；“同一调用” = 工具名 + 参数完全相同）：

| 模式 | 判定 | 提醒 | 停下 |
|---|---|---|---|
| 原地重复 | 同一调用连续出现，**结果也一样** | 3 次 | 5 次 |
| 同样的错 | 同一调用连续报错（结果不一定一样） | 3 次 | 5 次 |
| 换参数还是错 | 同一个工具连续报错，参数各不相同（bash 除外：命令失败是常态） | 4 次 | 8 次 |
| 来回摇摆 | 最近的调用是 A、B、A、B、A、B 这样两个动作交替 | 6 次 | 10 次 |

**其他方案的比较**：

| 方案 | 怎么做 | 好处 | 代价 | 代表 |
|---|---|---|---|---|
| ① 按模式计数 | 数重复、连续报错、来回摇摆 | 便宜、确定、能离线测、重放不变 | 只认“字面上的重复”，换个写法打转认不出 | OpenHands、Hermes、DeepSeek Harness |
| ② 执行前拦截 | 调用算哈希，重复到次数就不执行 | 连执行成本都省了 | 误拦合理重试（轮询服务状态） | OpenClaw |
| ③ 看有没有进展 | 看结果有没有带来新信息 | 能认出“换着花样打转” | “新信息”很难定义 | Hermes 的“只读工具反复无进展” |
| ④ 让模型自己反省 | 每 N 步问“进展如何、是不是卡住了” | 简单、懂语义 | 依赖模型老实；定期打断正常工作 | smolagents 定期规划 |
| ⑤ 另请模型当裁判 | 起疑时让便宜模型看轨迹判断 | 最懂语义 | 花钱、有延迟、不确定（裁决要记进账本） | 审批上的趋势，防失控上还少 |
| ⑥ 交给人决定 | 暂停问人“继续还是停” | 不误杀，人最清楚 | 需要有人在 | OpenCode doom_loop |
| ⑦ 让它看见剩余预算 | 上下文里写明还剩多少步、多少 token | 主动收尾，不被硬砍 | 不能识别打转 | Codex（开发中）、Claude task budget |

**我们的做法：分层组合**（和权限的三级结构同一个思路——便宜的规则挡大部分，拿不准的升级）：

```
第 1 层（每步，免费）：① 按模式计数 → 到“提醒”次数插提醒
第 2 层（到“停下”次数）：
        有人值守（交互模式）→ ⑥ 暂停问人：继续 / 停下 / 给个提示
        无人值守（--yes、子 Agent）→ 停下，状态 stuck
第 3 层（一直开着）：⑦ 剩余步数或预算少于 20% 时提醒一次，让它开始收尾
以后可选：⑤ 裁判模型，接在第 2 层“问人”的位置（适合无人值守）
```

- ① 便宜确定，当底座；它认不出语义上的打转，由 ⑥（以后 ⑤）补。
- ⑥ 几乎不用新代码：“等人”本来就是内核的正式状态（`WaitStarted`），和工具审批同一套；问人时选“继续”，这一段重复就清零重新计数；给了提示，提示作为一条输入交给模型；选“停下”，任务以 `stuck` 结束。
- ⑦ 解决的是另一件事：防“做到一半被预算砍断”。现在是用完才给一次收尾机会，提前提醒更好（第 14 课：优雅收尾比硬停好）。每个任务只提醒一次。
- 不用 ②（误杀合理重试）和 ④（定期打断、模型自评不可靠）。

**提醒怎么写**：说清是哪种模式、哪个调用：“你已经连续 3 次调用 `bash(npm test)`，结果都一样。重复不会有新结果：换个思路，或者说明卡在哪里、需要用户做什么。”同一段重复只提醒一次。

**“结果一样”怎么比**：比较前去掉每次都会变的部分（如 bash 结果里的“用时 X 秒”），否则同样的失败每次都“不一样”。

**为什么放在 Policy 而不是执行者**：判断只依赖账本里的记录，是纯计算，和内核其他规则一样能离线测试、崩溃后重放结果不变。

## 三、共用的“提醒”机制

两件事最后都落到“插一条提醒再问模型”。在内核里做成通用的一步，放在“问模型”（规则 10）之前：

```
policy.guard(state) -> Stop(reason) | Escalate(reason) | Nudge(kind, text) | None
```

- `Stop` → 结束任务（`stuck`）。
- `Escalate` → 开始一个阻塞的等待（`WaitStarted(kind=stuck)`），交互模式下终端问人；回答“停下”则结束（`stuck`），“继续”则这段重复清零，附带的提示作为一条输入交给模型。
- `Nudge` → 追加一条 `InputReceived(source=policy, nudge=kind)`，然后照常问模型。
- 优先级：停下 / 问人 > 死循环提醒 > todo 提醒 > 预算提醒；一次只插一条。
- **防止一轮插好几条**：只在“上次模型回复之后还没有新输入”时检查；插了一条提醒就算有了新输入，下一次决策直接去问模型。
- **冷却**：每条提醒在账本里带 `nudge` 类型，`fold` 记下它是在第几步插的；同一类型要隔够步数才会再插。

完成判定的“打回”走的是现成的 `on_model_done → Continue`，同样是插一条 `source=policy` 的输入。

提醒都追加在末尾，不动前缀，缓存不受影响。

## 四、放在哪一层

| 部分 | 位置 |
|---|---|
| `todo_write` 工具、清单校验和渲染 | `weaver/todo.py` |
| 从账本推导当前清单、最近的工具调用记录、提醒冷却 | 内核 `fold`（`State` 多几个字段） |
| 四种卡死模式的判定 | `weaver/guards.py`（纯函数） |
| `guard` 关卡、默认的 todo 提醒和完成打回 | Policy |
| `Stop` / `Nudge` 的处理、`stuck` 状态 | 内核 `decide`（新增一条规则） |
| 清单显示 | CLI |

## 五、测试

todo：

1. 工具：整张提交、状态校验、最多一个 in_progress、渲染。
2. 清单来自账本：崩溃恢复、`-s` 接着跑后清单还在；报错的 todo_write 不算。
3. 10 步没更新 → 插提醒（带当前清单）；更新后清零；冷却生效。
4. 压缩后清单没做完 → 插提醒补回清单。
5. 说完成但清单没做完 → 打回一次；同一张清单第二次放行；清单全勾了直接放行。

防死循环：

6. 四种模式各自在提醒阈值插提醒、在停下阈值结束（`stuck`）。
7. 有进展的重复（同一调用、结果不同）不算原地重复。
8. bash 换参数报错不算“换参数还是错”。
9. 提醒冷却：提醒后没有再累积够次数不重复提醒。
10. 子 Agent 被判卡住，状态交回主 Agent。
11. 提醒追加在末尾，前缀不变。
12. 交互模式到“停下”次数时问人：继续 → 清零重新计数、提示作为输入；停下 → `stuck`；无人值守直接 `stuck`。
13. 剩余步数或预算少于 20% 时提醒一次。
14. 真实验证：给一个做不到的任务（比如“让这个故意写死失败的测试通过，但不许改测试和被测代码”），看它是否被提醒、换思路或停下，而不是烧光步数。

## 进度（2026-10-01）

已实现：`weaver/todo.py`（todo_write、校验、渲染）、`weaver/guards.py`（四种卡死模式，纯函数）；内核加 `stuck` 状态、`Stop` / `Escalate` / `Nudge`、`State` 里的清单和工具结果记录、提醒冷却、`AddInput.meta`；默认 Policy 的 `guard`（卡死 → todo → 预算）和 `on_model_done`（清单没做完打回一次）；CLI 显示清单和 `⚑` 提醒，卡住时问“继续 / 停下 / 给提示”；交互模式（非 `--yes`）卡住先问人，`--yes` 和子 Agent 直接 `stuck`。测试见 `tests/test_todo_loop.py`（15 项）。

实现时的补充：比较“结果一样”时还会去掉子 Agent 结果里的“N 步，N token”；预算提醒每个任务一次，已经在收尾时不提醒。

真实验证（claude-sonnet-4.5 及两个小模型）：

| 任务 | 结果 |
|---|---|
| 三件事（修 bug、加函数、加测试） | 7 步做完，没用 todo |
| 五个函数 + 测试 | 6 步做完（两次大编辑一次写完），没用 todo |
| “一直重试直到通过”（测试依赖一个不存在的服务） | Sonnet 没有打转：自己写了个 `server.py` 起服务，测试通过 |
| 同上，禁止写文件和起进程，用 ministral-8b / 3b | 试 1~2 次就停下说明，没有打转 |

结论：

- 这个规模的任务，模型不写清单是合理的（工具说明本来就说“一两步能完成的别用”，而它一次编辑就能写完好几处）；清单的价值要在几十步的长任务里才显出来，还没有真实数据。
- 三个模型、三种设置都没能诱导出真正的打转：现在的模型在简单场景里很少原地打转。防死循环是**兜底**，平时基本不触发；它的路径目前只由离线测试覆盖。
- 没有为了“让它用清单”去改提示词：短任务强行写清单只会多花步数。
